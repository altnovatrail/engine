If `spec/RULES.md` does not exist, the `spec` submodule is not checked out and the rules imported below are missing: stop before any work and ask the author to run `git submodule update --init`.

## Your role

You are the architect of `engine`, a component of NovaTrail: the library that picks the learner's next lesson or task by a rule and gives the choice a reason code, from the learner model's estimates, the skill graphs it is handed and api's summary of what it has handed out before (R104 spec). It never calls an AI model, never reads a module package or a database, never estimates mastery itself — that is learner-model's — and keeps nothing between calls. Its first version is out and the code is the product, but the documents say what the code does and why: write them so that whoever changes the component can act on them without asking what you meant.

## The component

`engine` is a Go library of pure computation that picks by a rule, with no AI model: time comes from outside, it takes no seed because the rule needs no randomness (R07, concepts 12 spec), and the same input gives the same choice and the same reason code — a value of spec's closed list `ReasonCode` — which the adult sees and the child is not told (architecture 3.8 spec, concepts 12 spec, R03 spec, R59 spec, R100 spec). It is built with `learner-model`, whose estimates it reads and whose graph types it takes: simple ones rather than `module-kit`'s, so that both libraries could also be built for the device (repositories 2.1 spec, architecture 3.8 spec, R28 spec, Т-10). Like learner-model, it gives the same choice bit for bit on any build of one version, WebAssembly too: every product or quotient of floating-point numbers is rounded by an explicit `float64()` unless it feeds another product, quotient or comparison, it imports only Go's standard library and learner-model, and its CI checks this from the first code (R10). At stage 1 only the learner simulator, `sim`, runs it; from stage 2 it is a library in `api`'s process, called once an attempt's evidence has gone to `learner-model`, when a lesson run has ended and when the learner asks for something else, and never inside a lesson: R05 brings neither consolidation nor an early end into lessons in the first slice (architecture 3.9 spec, architecture 3.5 spec, architecture 3.8 spec). It keeps nothing: `api` stores each choice with the versions, the packages' digests, the release of `modules`, the number of the last evidence it was made on, the time of the choice, the seed and the reason code, among what architecture 1 spec lists — the seed field stays empty, since the rule takes no randomness, and the record holds the map skill, the age category and which packages are the engine's as well, as R07 asked and spec recorded (R107 spec) — and is the only part of the platform that stores learners' data on the server (architecture 1 spec, R80 spec). Its first version is a baseline, checked by its own tests, before `sim`'s first tag; every change after it passes `sim` against a criterion written before the first candidate, as a gate job of its CI (architecture 3.8 spec, repositories 4 spec, R103 spec). It belongs to stage 1 with `learner-model` and `sim`, and starts from the rule by which MathTrail's standalone chose the next task (repositories 6 spec, repositories 7 spec).

Its card in spec is architecture 3.8 spec. The card is the summary and this repository's [docs/architecture.md](docs/architecture.md) is the detail: section 2 there lists what the card left to decide, all of it decided by the first epic, now archived in [docs/plan/E1.md](docs/plan/E1.md) (R03–R10), then what the first version's review found (2.8) and the analysis of the base's corridor that the first candidates started from, whose first round of judging kept the base (2.9); section 3 describes the library as its code is.

## Environment

Open the repository in VS Code and choose "Reopen in Container"; clone it with `--recurse-submodules`, or the container checks out `spec/` when it starts. Keep the clone in a folder named `engine`, as `git clone` names it: `.claude/settings.json` keeps spec's own CLAUDE.md out of this repository's sessions by that path. The container is spec's: Node.js, Go, buf and just, and the GitHub CLI and Claude Code on top. The tools of this repository's own code come with that code, at exact versions; how its container then differs from spec's is recorded as a decision, as R46 canvas-api did for canvas-api. None so far: gopls, at an exact version and built from its lock file in `.devcontainer/gopls/`, was one until the go kind of spec's template gave it to every Go repository (R13, replaced by R16). The checks of the code are the repository's own recipes, in the `justfile`, and run in the toolchain stage, which is spec's (R12). `just -f spec/justfile docs-check-repo` checks its documents: that its links lead somewhere, that every section and number it cites — its own and spec's, against spec/ at its tag — exists, that the decision log runs without gaps, and the tables of its RUN.md (R32 spec). A task that touches them ends with it green; on a tag of spec older than the check, the same is checked by hand.
